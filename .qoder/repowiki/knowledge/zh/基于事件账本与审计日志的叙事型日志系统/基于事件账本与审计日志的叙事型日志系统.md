本仓库没有使用 Python 标准 logging 模块或第三方日志框架，而是构建了一套以「事件溯源 + 审计 JSONL + Markdown 叙事日志」为核心的持久化日志体系。所有运行时输出都落盘到存档目录的文件中，而非 stdout/stderr。

1. 系统与架构
- 事件账本（event_log.md）：每个回合的 Python 结算事件以 Markdown 代码块中的 JSON 追加写入，由 `engine_runtime/events.py` 提供 `append_event`/`parse_events`/`apply_event` 等读写与状态投影函数。SQLite（campaign.sqlite3）作为唯一真相源，Markdown 事件文件用于人类可读重放。
- 对话与小说日志（conversation_log.md、novel_draft.md）：`engine_runtime/narrative_log.py` 将玩家原始输入、GM 完整回答与 Python 结算事件原子性地追加到两个 Markdown 文件中，同一回合仅允许记录一次，并通过 `<-- narrative-turn:{turn} -->` 标记防重入。
- 决策审计（decision_audit.jsonl、decision_audit.md）：`engine_runtime/audit.py` 为每回合生成结构化审计记录，包含 player/llm/python/joint/player_database_impact 五个维度，并计算 before/after 状态差异（仅 player/inventory/base/npcs/factions/relationships/meta 七个区），同时维护人类可读摘要。
- 工具层 CLI 输出：tools 目录下脚本通过 `print()` 向 stdout/stderr 输出 JSON 或错误信息，属于命令行交互输出，不属于引擎内部日志。

2. 关键文件与职责
- engine_runtime/narrative_log.py：回合级叙事日志写入、GM 回答合法性校验（禁止内部协议字段泄漏）、原子性双写 novel_draft.md + conversation_log.md。
- engine_runtime/audit.py：审计记录结构定义、JSONL 追加与去重、Markdown 摘要生成、执行/拒绝两类审计构建器。
- engine_runtime/events.py：标准事件格式、Markdown 事件账本追加/解析、事件到状态的确定性投影（含时间推进、NPC/势力调度、遭遇战清理、叙事压力指标等）。
- engine_runtime/state.py：GameState 封装 YAML 快照与 SQLite 事件存储，统一 apply_and_append/commit_pending/save 流程，并在初始化时从 event_log.md 回灌历史事件。
- tools/*：CLI 工具直接 print JSON 结果或错误，不经过上述日志子系统。

3. 约定与约束
- 事件必须携带 turn/timestamp/event_id/type/data 字段，且数据变更通过 data.* 显式增量表达，叙述文本不参与状态计算。
- 同一回合只能记录一次叙事日志；重复写入会抛出 ValueError。
- GM 回答不得包含内部协议关键词（预览合法、未结算、dry-run、action_id、确认执行、SQLite、Python），否则校验失败。
- 审计记录 audit_id 全局唯一，重复写入会拒绝。
- 状态差异比较仅覆盖 AUDIT_STATE_KEYS 指定的七个区域，meta.last_played 等易变键被排除。
- 所有日志均为 UTF-8 文本，换行统一为 \n，JSON 使用 ensure_ascii=False 保留中文。

4. 与标准 logging 的关系
仓库未引入 logging/structlog/loguru 等框架，也没有统一的 log level 管理。调试与诊断完全依赖可重放的 Markdown/JSONL 文件和 SQLite 事件账本，以及 tools 脚本的 stdout 输出。
