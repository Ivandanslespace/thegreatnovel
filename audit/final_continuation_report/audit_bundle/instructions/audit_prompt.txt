二、报告状态词
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

报告中的每一项重要结论必须使用以下状态之一：

- VERIFIED_PASS：
  已运行、已检查，并有具体证据支持。

- VERIFIED_FAIL：
  已运行或已检查，明确失败。

- WARNING：
  没有构成硬失败，但存在质量、连续性、公式、风格或后续风险。

- NOT_RUN：
  本次没有运行，不能声称通过。

- NOT_AVAILABLE：
  需要的日志、文件、状态或历史不存在，无法复核。

- INFERENCE：
  这是根据现有证据作出的推断，不是直接记录的事实。

- AUTHOR_DECISION：
  这是作者明确决定，不是系统计算结果。

禁止使用含糊表达，例如：

- “应该没问题”；
- “大致通过”；
- “看起来已经测试”；
- “理论上符合”；
- “基本完成”。

凡没有证据的内容，一律标记为 NOT_RUN、NOT_AVAILABLE 或 INFERENCE。

1. Canon Validator
2. Timeline Validator
3. Knowledge Validator
4. Character Validator
5. Economy / Power Validator
6. Contract Validator
7. Debt Validator
8. Payoff Validator
9. Repetition Validator
10. Style Validator

每项必须提供：

- status；
- validator implementation path；
- exact command；
- exit code；
- validation report path；
- inputs；
- errors；
- warnings；
- evidence；
- 是否自动修复；
- 自动修复修改了什么；
- 最终是否重跑。

重点说明：

- Validator 是真实代码检查，还是 Codex 自我评审；
- 哪些 Validator 是 deterministic；
- 哪些依赖 LLM；
- 哪些只是文档中的占位；
- 哪些根本没有实现。

禁止把“Codex读完后认为没问题”描述为正式 Validator 通过。

# 14. Test and Static Analysis Evidence

运行项目中已经存在、且不会破坏正式状态的测试和静态检查。

必须记录实际命令、完整退出码和结果。

至少检查项目实际支持的：

- pytest；
- Ruff；
- Mypy 或 Pyright；
- migration check；
- schema validation；
- replay test；
- source immutability check；
- end-to-end continuation test。

不要安装新依赖或改配置来让检查通过。

如果缺少依赖：

- 标记 NOT_RUN；
- 记录缺失内容；
- 不得擅自安装后改变环境。

报告格式：

| Check | Command | Exit code | Passed | Failed | Skipped | Status | Log path |

完整日志放入证据包，报告只放摘要。

禁止声称“全部测试通过”，除非有：

- 实际命令；
- exit code 0；
- 完整日志；
- 测试数量。

# 15. Canon Commit, Snapshot, Replay and Export

明确回答：

- 是否执行 approve；
- 谁授权 approve；
- 授权文本在哪里；
- 是否执行 Canon Commit；
- canon_commit_id；
- commit 前状态；
- commit 后状态；
- 应用了哪些 events；
- 是否生成 snapshot；
- snapshot_id；
- snapshot hash；
- 是否执行 replay；
- replay 命令；
- replay exit code；
- replay 前后 projection 是否一致；
- 是否执行 export；
- export 路径；
- export hash；
- export 是否包含正确的原文和续写；
- book 原文件哈希是否保持一致。

如果没有作者明确授权却写入了正史，必须标记 VERIFIED_FAIL。

如果只是草稿，不得用“已完成续写”掩盖“没有进入正史”的事实。

列出所有：

- 修改文件；

- 未跟踪文件；
- staged 文件；
- ignored workspace 文件；
- 数据库变化；
- 草稿变化；
- 正史变化；

提供：

- git diff --stat；

- 关键 diff；
- 最近相关 commit；
- branch；
- HEAD；
- remote。

不要在本次报告中替用户创建提交。

# 17. Style Continuity Audit

将原文最近章节与续写正文比较，至少报告：

- 简体或繁体；
- 叙事人称；
- POV；
- 叙事距离；
- 章节长度；
- 平均段落长度；
- 对话比例；
- 系统提示格式；
- 动作描写密度；
- 心理分析密度；
- 解释性旁白密度；
- 章节结尾钩子；
- 高频句式；
- 明显禁用词；
- 是否出现现代AI式总结语气；
- 是否出现比原文明显更精致或更书面的问题；
- 是否大段复制原文。

区分：

- 可计算统计；
- LLM 风格判断；
- 人工观察。

不得把简单字符统计描述成完整文风一致性证明。

# 18. Narrative Quality and Formula Audit

依据项目宪法，对续写结果进行一次诚实自审。

逐项回答：

1. 当前控制缺口是什么？
2. 本章是否使规则更可理解？
3. 主角非对称杠杆是否真正改变了结果？
4. 旧成果是否产生复利？
5. 是否出现真实关系或地位反转？
6. 是否完成了阶段跃迁，还是仅做局部推进？
7. 压力是否先积累后释放？
8. 爽点是否成熟？
9. 奖励或胜利是否改变了后续行为？
10. 是否留下更高层问题？
11. 是否一次解决了过多矛盾？
12. 是否重复近期同类结构？
13. 主角是否主动决定，而不是被剧情推动？
14. 风险是否仍可信？
15. 新悬念是否超过偿还能力？
16. 本章是否产生不可逆进展？
17. 重大兑现是否创建 Aftershock Obligations？
18. 下一章最应该展示什么后果？

每项必须引用正文和状态证据。

# 19. Aftershock Obligations

列出所有续写结果产生的后续义务：

- obligation_id；
- 来源事件；
- 最迟兑现章节；
- 必须展示的后果；
- 不得如何回收；
- 当前状态；
- 是否已写入数据库；
- 是否只存在于报告文字；
- 若不兑现会破坏什么。

例如但不限于：

- 其他人物对主角实力公开后的行为变化；
- 重伤角色的医疗后果；
- 死亡怪物的尸体或掉落处理；
- 战场资源结算；
- 敌方重新评估主角；
- 主角暴露能力后的社会风险；
- 更大威胁的推进。

不能只写“无”。

至少检查：

- 原文章号异常；
- source parser 不确定性；
- 低置信度 Canon；
- 未审核 inference；
- 缺少的来源；
- 未实现的 Validator；
- 公式输入由 LLM 主观给分；
- 状态数据库与正文不同步；
- 精确经验或掉落规则不明；
- 文风漂移；
- 候选结构重复；
- 合同与成稿偏差；
- 未完成的 aftershock；
- 未运行的测试；
- Git 工作区污染；
- 正史提交权限问题；
- replay 不一致；
- export 问题。

对每个问题提供：

- severity；
- evidence；
- impact；
- 是否阻断继续续写；
- 推荐下一步；
- 是否需要作者决定。
